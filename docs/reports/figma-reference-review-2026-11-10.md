## Findings that affect the architecture

1. **Reusable visual structure, different product.** The reference uses rounded cards, pale backgrounds, dark text, lime accents, Inter text styles, pill controls, photo-led catalog cards, a dark desktop sidebar and mobile bottom navigation. Reuse hierarchy, spacing rhythm and action grouping. Retain GlycoLens branding/palette and create its own tokens; do not copy logos, photos, exact dimensions or sample values. Font inspection shows Inter variants, but it does not require adding that font dependency.
2. **Onboarding collects too much for our current use.** Its steps include signup, body measurements, activity, weight goals, conditions/allergies and review. The useful pattern is progressive disclosure and editable review. GlycoLens needs authentication, confirmed timezone/units, available data source and research/privacy acknowledgements, with optional food preferences/goals. This does not justify required diagnosis, weight, medication or household questionnaires.
3. **Home needs a different priority.** Reference energy rings and recipe discovery work as secondary modules. GlycoLens should put source/freshness, recent glucose and a clearly uncertain forecast first, followed by consumed-meal totals and recipe discovery. A fixed 2,000-kcal target, missing-data zeros and invented recommendations are inappropriate defaults.
4. **One meal composer can serve multiple entry points.** Quick add, portions/slots, action sheets and confirmation are useful. Search, scan, recipe analysis and detail pages should all feed the same reviewed composition/save contract. Copying, planning, cooking, forecasting and eating must not become interchangeable events.
5. **Search/detail coverage is useful but incomplete across devices.** Product detail actually exists within the supplied product-search group. Recipe/product search has mobile references but no separately supplied full desktop counterparts; notifications has only a desktop reference. Tablet layouts are absent. Build these from shared components and content rules, not stretched screenshots.
6. **Navigation is inconsistent between reference states.** Bottom bars alternate Nutrition/Recipes/Planning/Logs/Grocery labels; desktop includes Budget, Grocery and AI tools. GlycoLens needs one route definition with Home, Search, Meal log, Forecasts and Nutrition, plus account destinations. Do not inherit every sidebar item as a feature commitment.
7. **Some reference claims conflict with GlycoLens safety boundaries.** Analyzer/filter/product frames use condition-friendly, hypertension-safe, family-safe and allergen grading; nutrition includes deficiency-style advice. Do not transfer these claims, infer a diagnosis or create glucose alarms. Ground facts in source records and show unknowns. Figma sample product/nutrition values are illustrative and are not validation fixtures.
8. **Responsive behavior cannot be inferred from two frame sizes.** Most full pages are 390px or 1280px wide. Fixed screen heights, mock status bars, native keyboard illustrations and overlay frames are presentation artifacts. GlycoLens needs fluid layouts, keyboard/focus behavior, safe areas, chart tables and explicit testing from 320px through wide desktop.

## Per-area adaptation

| Area | Keep as a reference pattern | GlycoLens adaptation / boundary |
|---|---|---|
| Onboarding | Step progress, grouped inputs, review/edit and completion | Minimal resumable server state; no required medical/body questionnaire |
| Home | Header, daily summary cards, discovery grid, quick add | Glucose/forecast first; eaten nutrition and source clock; no household/shopping |
| Meal logging | Date navigation, meal sections, entry sheet, portion review, action confirmation | Separate planned/eaten/scenario state, durable saves, revisions and explicit copy semantics |
| Recipe detail | Hero/facts, ingredient quantities, preparation and nutrition sections | Serving/yield/source review then meal/forecast action; guided cooking deferred |
| Recipe search | Entry/recent, autocomplete, chips, filters, sort and results | Validated catalog and supported data filters; no clinical-safe categories |
| Analyzer | Input selection, text editing, processing and result hierarchy | Resolved ingredients and deterministic totals; no LLM nutrients or arbitrary URL/photo import |
| Products | Product/recipe tabs, count, detail tabs, filter and empty recovery | Canonical product, pack/serving basis and provenance; no retail inventory or safety guarantees |
| Nutrition | Day summary and seven-day visualization | One consumed-meal aggregate, coverage and optional goals; no automatic deficiency advice |
| Profile | Account/activity grouping, editable preferences, settings/logout | Identity/preferences/source/privacy; favorites; no family/child profiles |
| Notifications | Event list, categories, timestamps, unread and mark-all-read | Owned in-app nonclinical events; delivery reminders require separate opt-in/work |

## Classification corrections and implementation gaps

- `505:7821` is a **1280px desktop recipe detail**, supplied twice. It is not a second mobile design.
- `536:5064`, `535:4981` and `527:4364` are small sheet/dialog/dropdown components under the request's desktop meal group, not full desktop pages.
- `1859:5479` is a **product detail page**, so product detail is represented even though its group is called product search.
- `279:2909`, `612:7126`, `279:7070` and `612:5234` are multi-frame sections, not single giant screens to reproduce.
- No supplied reference defines GlycoLens glucose forecasting, uncertainty interpretation, immutable model inputs, simulator source clocks or personal outcome retrieval. Those remain our own domain design and existing scientific contracts.

## Outcome and next action

The documentation now defines the target routes, shared shell/components, onboarding, schema/API extensions, responsive rules and staged acceptance in [responsive UI architecture](../architecture/responsive-webapp-ui.md). The current executable single-page app remains unchanged. Begin with Auth/preferences and the shared shell, preserve the working demo, then extract existing meal/forecast features. Activate catalog-dependent pages only after the corrected release gate. See the [handoff](../tooling/responsive-ui-architecture-handoff-2026-11-10.md) for verification and remaining dependencies.
